# Архитектура приложения

Проект намеренно не использует фреймворки, сборщик и сервер. Все файлы подключаются обычными тегами `<script>` в `index.html` и выполняются по порядку.

## Порядок загрузки

1. `locales/ui.js` регистрирует языки и текст интерфейса.
2. Файлы вида `locales/en.js` добавляют названия событий и состояний на соответствующем языке.
3. `data/choice-systems.js` создаёт специальные повторяемые наборы решений.
4. Пять файлов `data/events/chapter-N.js` добавляют главы с планируемыми событиями в `PLANNER_CHAPTERS`.
5. `data/state-catalogue.js` создаёт справочник доступных состояний.
6. `data/initial-state.js` задаёт начальные значения.
7. `data/planner-data.js` объединяет данные в `PLANNER_PAYLOAD` и задаёт отображаемую версию приложения.
8. `js/i18n.js` выбирает язык и накладывает только текстовые поля локали.
9. `js/route-file.js` проверяет минимальный формат переноса выбранных решений.
10. `js/app.js` проверяет условия, рассчитывает маршрут и строит интерфейс.

Такая последовательность сохраняет запуск через `file://` и позволяет читать события отдельно от алгоритмов.

## Основные части `js/app.js`

### Модель состояния

- `initialState()` создаёт начальное состояние;
- `snapshotState()` делает снимок для отображения переходов;
- `recalculateDerived()` рассчитывает производные показатели сословий.

### Условия

- `evaluateCondition()` проверяет одно условие;
- `evaluateGroup()` объединяет обязательные условия и альтернативы;
- `groupAvailability()` учитывает возможность открыть условие за очки;
- `choiceAvailability()` возвращает итоговую доступность выбора и требуемые расходы.

### Последствия

- `applyEffect()` применяет один декларативный эффект;
- `setStatus()` изменяет постоянное состояние персонажа только при явном эффекте;
- `applyCreedChanges()` применяет последствия решений Кредо;
- `payAndApply()` сначала списывает подтверждённые расходы, затем применяет выбор.

### Пересчёт маршрута

`replay()` является центральным алгоритмом. Он проходит события в порядке записей, формирует состояние до и после каждого события, проверяет доступность, применяет выбранные решения и останавливается при автоматическом финале. Общий `occurrenceKey` не позволяет одному событию повторно сработать в следующей главе.

Функция не изменяет исходные данные из `data/`; результат хранится отдельно в `replayResult`.

### Представление

- `conditionText()` и `effectText()` создают понятные подписи;
- `requirementsHtml()` и `effectsHtml()` отображают блоки условий и последствий;
- `sceneHtml()` создаёт карточку события;
- `buildTimeline()` строит ленту один раз;
- `refreshTimeline()` обновляет состояние карточек после изменения выбора.

Строки из данных экранируются функцией `escapeHtml()` перед помещением в HTML. Публичные файлы данных всё равно следует считать доверенной частью приложения и не заменять непроверенными копиями.

### Навигация и история

- `renderAttributeBar()` обновляет панель характеристик;
- `renderStatePanel()` показывает отличия от начального состояния;
- `renderHiddenScenesPanel()` перечисляет скрытые события;
- `relevantHistoryItems()` ищет прошлые решения, влияющие на целевое условие;
- `renderChoiceHistory()` строит окно исправления маршрута.

### Локальное хранение

- `save()` записывает выборы и настройку шапки в `localStorage`;
- выбранный язык сохраняется отдельно и не меняет формат маршрута;
- `exportRouteMemo()` создаёт локальную текстовую памятку;
- сетевой обмен и серверное хранение маршрута отсутствуют;
- внешняя ссылка поддержки открывает Tribute только после явного клика и не выполняет фоновых запросов.

### Перенос маршрута

- `js/route-file.js` записывает и читает версионированный JSON-формат;
- в JSON входят только идентификаторы событий и выбранных вариантов;
- `js/app.js` сопоставляет их с текущими данными, пропускает неизвестные записи и заново рассчитывает маршрут;
- TXT-памятка предназначена только для чтения и не используется для импорта;
- файлы обрабатываются локально и не отправляются на сервер.

## Локализация

Механика хранится в одном экземпляре в `data/`. Файл локали содержит только подписи, поэтому перевод не может изменить условие, последствие или порядок событий.

Для нового языка:

1. добавьте язык и перевод интерфейса в `locales/ui.js`;
2. создайте `locales/<код>.js`, используя `locales/en.js` как пример структуры;
3. сохраните существующие ключи событий, вариантов и состояний, изменяя только отображаемый текст;
4. зарегистрируйте локаль в `window.PLANNER_LOCALES.languages`;
5. подключите новый файл рядом с `locales/en.js` в `index.html`;
6. выполните `node scripts/validate-project.mjs`.

Файл локали не должен содержать условия, последствия или другую механику. Если для какого-либо названия нет надёжного варианта на новом языке, лучше оставить его непереведённым и отметить это в Issue.

## Где вносить изменение

| Задача | Файл |
| --- | --- |
| Исправить выбор, условие или последствие | `data/events/chapter-N.js` |
| Исправить ежегодное дело или поездку | `data/choice-systems.js` |
| Переименовать характеристику или статус | `data/state-catalogue.js` |
| Изменить начальное значение | `data/initial-state.js` |
| Изменить расчёт доступности или последствий | `js/app.js` |
| Изменить формат переноса маршрута | `js/route-file.js` |
| Исправить текст интерфейса | `locales/ui.js` |
| Исправить английское игровое название | `locales/en.js` |
| Изменить внешний вид | `assets/styles.css` |
| Изменить статическую разметку | `index.html` |
